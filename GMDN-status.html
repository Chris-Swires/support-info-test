Initial Import Specification

Agreed

The initial import converts the full GMDN v26.2 dataset into a valid SNOMED CT RF2 snapshot package, preserving GMDN names, definitions and status faithfully as SNOMED CT components, and making every device type browsable, searchable and ECL-queryable in Snowstorm.

DECISION · OPTION 1

Separate extension — full GMDN content, duplication accepted

Of the two options assessed, we have decided on Option 1: import the complete GMDN dataset into its own extension, ignoring conceptual overlap with SNOMED CT International device content. Overlap is conceptual, not structural — every FSN carries the distinguishing (GMDN) semantic tag so no duplicate FSN can exist by construction, and all concepts are primitive, so no reasoner will conflate GMDN concepts with their International near-equivalents. This trades conceptual tidiness for implementation simplicity; the existing SNOMED CT → GMDN map already links corresponding concepts explicitly where a correspondence is known.

Root placement & hierarchy

A single GMDN root concept is created as a child of 260787004 |Physical object|; all 31,092 GMDN terms sit as direct children — a deliberately flat, two-level IS-A hierarchy that preserves the integrity of the original GMDN model.

Description modelling

Each GMDN term generates three descriptions:

  • FSN — GMDN term name with the (GMDN) semantic tag
  • Synonym — the bare GMDN term name (preferred term)
  • Text definition — the full GMDN definition, verbatim

Modelling & refsets

  • Both US and GB English language refsets included (93,276 × 2 = 186,552 rows)

Assumptions in the import script

Blank component IDs

Concept, description, OWL axiom and language refset IDs are left blank in the RF2 files; Snowstorm auto-generates valid SCTIDs from the branch configuration on import. This avoids needing a pre-allocated namespace, but a formal GMDNA namespace is the intended end state (see Next Steps).

Root cross-reference resolution

Because IDs are blank at generation time, OWL axioms that reference the GMDN root face a bootstrapping challenge — the script assumes this is resolved via a two-pass approach or a known root ID before the full import.

Obsolete term handling

GMDN terms flagged obsolete in the GMDN source data become inactive concepts with inactive axioms, but their descriptions remain active — retired device names stay searchable for historical record linkage and provenance.

Faithful, generic modelling

GMDN names, definitions and status flags are carried over verbatim; no SNOMED CT defining-attribute modelling is added. Every term carries only a generic IS-A to the GMDN root, and GMDN categories are not recreated as parent concepts in this first pass.

Snapshot-only package

The deliverable is an RF2 Snapshot package (concepts, descriptions, OWL expression refset, language refsets) with effective date 20260429, loaded via Snowstorm batch import — no Full or Delta files at this stage.

Set up the code system Up next

Create a dedicated GMDN code system in Snowstorm with its own branch (e.g. MAIN/SNOMEDCT-GMDN), dependent on the appropriate International Edition release, so the extension content is cleanly separated and independently versionable.

Establish a GMDNA namespace Up next

Allocate a formal SNOMED CT namespace for the GMDN Agency and configure it on the branch, so that all generated SCTIDs are properly attributed to GMDNA rather than relying on ad-hoc ID generation.

Future Work

Beyond the checkpoint

Open questions and enhancement options to be agreed jointly once the initial extension is live.

?

Maintenance model

How is the extension kept in sync with GMDN, whose data is updated ad hoc in real time rather than on a fixed release cycle? Who owns the update pipeline, how are new, changed and newly-obsoleted GMDN terms picked up as they occur, and what does the delta process look like?

?

Release frequency

Decide the release cadence for the GMDN extension: GMDN updates ad hoc in real time, while SNOMED CT International releases monthly — options include tracking the monthly International cycle, batching GMDN changes on an independent schedule, or something closer to continuous delivery.

Possible move to Option 2 — inactivating International duplicates

A more curated future state: keep the full GMDN import, but additionally inactivate corresponding SNOMED CT International device concepts within the extension branch, so the combined view shows exactly one active concept per device type (the GMDN-sourced one). Inactivation applies within the extension only — the International Edition itself is untouched. This requires a reliable matching exercise between GMDN terms and International device concepts, and would be considered once Option 1 is bedded in.

Expanding the hierarchy & GMDN categories

Options for enriching the deliberately flat first-pass hierarchy: introduce intermediate levels using GMDN's category metadata, and bring GMDN categories into the extension as parent concepts so devices can be queried by category via ECL. Category-level IS-A relationships would be added in a subsequent pass without disturbing the original term set.
