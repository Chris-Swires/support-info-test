AI makes tickets easy to write and hard to read. Let's agree a simple standard so every ticket is concise, clear and ready to act on.

The problem · 2 min

We use AI to expand a ticket,
then AI to shrink it again

1 · Creator

Gives AI a few lines of notes. Gets back 600–1,000 words with headings, options, risks and code. Assigns it without cutting it down.

→

2 · Recipient

Can't tell what's actually needed. Pastes it into AI and asks for a summary, or reads for five minutes to find the ask.

→

3 · Result

Two rounds of AI to send a three-line message. The detail that matters is hidden, and nobody is sure which parts were checked.

The issue isn't AI. It's unreviewed AI output being assigned to someone else to deal with.

Example 1 · 1.5 min

The first paragraph was the ticket

Likely AI-generated

INFRA-18319 · Stop nginx needing DNS at startup

  • 1,002 words, 14 headings, 3 code blocks
  • Sections: Summary, Incident, Root cause, Proposed change, Optional follow-ups, Implementation steps, Testing, Acceptance criteria, Risks, References
  • Opens with a short human-written paragraph, then repeats it as an AI "Summary" and "Incident" section
Rewritten · 70 words
nginx: don't need DNS at startup, and restart on failure

Why: On 13 Nov a libc6 security update restarted nginx and networkd together. nginx couldn't resolve its upstream during the brief DNS gap, so prod-cis and prod-us-request stayed down until restarted by hand.

Done when:

  • Upstreams resolve at request time, not at startup
  • systemd restarts nginx if it fails to start
  • Tested by restarting nginx with DNS unavailable

Implementation detail, config snippets and risks are useful, but they belong in a comment or linked page, not in the description the assignee reads first.

Example 2 · 1.5 min

A 1,000-word ticket for a three-line fix

Likely AI-generated

MAP-1789 · mapping-rest — Debian packaging fix

  • 1,001 words, 13 headings, 12 code blocks
  • Includes the full config of a different service as "the gold standard", a side note, a three-way comparison table and four numbered changes
  • The actual ask is in the second paragraph of the summary
Rewritten · 75 words
mapping-rest: package fails to install on a fresh host

Why: apt install mapping-rest aborts. The .deb ships no supervisor config, and preinst/postinst call supervisorctl unguarded under sh -e.

Done when:

  • Package ships /etc/supervisor/conf.d/mapping-rest.conf
  • supervisorctl calls in preinst/postinst can't abort the install
  • Clean install and upgrade both succeed

Reference: classification-service/src/deb does this correctly. Full analysis attached.

Lessons from the sample · 1.5 min

Honest labelling helps. Empty templates don't.

AI-generated (declared)

INFRA-18192 · QA Stats deep links return 404

Starts with a banner saying it was written with AI and not yet verified by a developer. Marks each piece of evidence as verified or inferred, and lists open items.

Worth copying: the label and the verified/inferred split.
Still to fix: 608 words. The problem and the fix fit in one screen.

Human-written, template only

PIP-1353 · RVF: Evaluate duckdb-engine feature from AU

Uses Summary / Context / Acceptance criteria headings, but each one repeats the title: "Evaluate the duckdb-engine feature from AU locally."

Lesson: a template only helps if each section answers its question. Short is fine; empty isn't.

Short human tickets work well when they say why. RAP-287 (129 words) gives what happened, why it matters and a numbered proposal. That's the bar.

Best practice · 2 min

What a good ticket must contain

1 · Title

Component + what's wrong or needed. Readable in a board column.

"mapping-rest: package fails to install on a fresh host"

2 · Why

One or two sentences: the problem, who it affects and how urgent it is.

3 · Done when

Three to five testable bullets. This is what the assignee will build and check against.

4 · Links

Related tickets, logs, Confluence pages, PRs. Link to them instead of pasting them in.

Add only when it helps

  • Steps to reproduce (bugs)
  • Constraints or deadlines
  • A suggested approach, kept short

Leave out of the description

  • Long root-cause analysis and code listings: use a comment or attachment
  • Several alternative options: pick one, or ask a question
  • Repeating the title as the summary
Proposal · 2 min

One template, under 200 words

Description template

Why
<1–2 sentences: problem, impact, urgency>

Done when
- <testable outcome>
- <testable outcome>
- <testable outcome>

Links
<tickets, logs, pages, PRs>

Notes (optional)
<steps to reproduce, constraints>

AI use
<None / AI-drafted, reviewed by NAME>

Prompt to give your AI tool

"Write a Jira ticket using this template: Why, Done when, Links, Notes. Keep it under 200 words. Write for an engineer who already knows the system. Don't include alternative options, background history or code unless I ask. Put any detailed analysis in a separate comment."

Most of the length comes from the prompt, so let's give the AI the template up front.

Could be set as the default description in Jira for INFRA, MAINT, PIP and RAP so it appears on every new ticket.

Taking responsibility · 2 min

If you assign it, you wrote it

Creators

  • Read the whole ticket before assigning it
  • Cut anything you wouldn't have typed yourself
  • Check facts the AI inferred, or mark them as unverified
  • Fill in the AI use line

Recipients

  • It's fine to send a ticket back as "unclear, please shorten"
  • Ask for the "Done when" if it's missing
  • Don't quietly rewrite it with AI. Raise it so the creator learns

Quick test

Could the assignee start work after reading for one minute?

Board refinement

Spot-check new tickets against the template at refinement or triage.

Lead by example

Leads and seniors use the template first. Others will copy what they see.
